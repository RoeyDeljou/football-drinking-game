# Deployment

**Live:** https://football-drinking-game-web.vercel.app — deployed 2026-09-24. Public, no deployment protection:
anyone with the link can play. Solo play works (a room's `minPlayersToStart` is set to `1` when created from the
web host flow), so this doubles as a quick way to sanity-check the live deploy yourself.

Two services, following the same Vercel + Render split already used by the sibling hub app:

```
apps/web (Next.js)  ──HTTPS/WSS──►  apps/api (Fastify + Socket.IO)  ──►  Render Postgres
     Vercel                              Render, Frankfurt                Render, Frankfurt
```

## apps/web — Vercel

- Project `football-drinking-game-web` under the `roeydeljou1-3768s-projects` account, imported from
  [RoeyDeljou/football-drinking-game](https://github.com/RoeyDeljou/football-drinking-game) (branch `master`).
- **Root Directory:** `apps/web`. Because this is an npm-workspaces monorepo and `apps/web` imports the *compiled*
  output of `@fdg/game-core` (not just its types), the zero-config Next.js build isn't enough — it needs to build
  the workspace's dependencies first:
  - **Install Command:** `cd ../.. && npm install`
  - **Build Command:** `cd ../.. && npm run build --workspace=packages/football-data --workspace=packages/game-core --workspace=apps/web`
- **Environment variable:** `NEXT_PUBLIC_API_URL=https://fdg-api-x9pw.onrender.com` (Production, Preview, Development).
- **Deployment Protection → Vercel Authentication: disabled.** It defaults on for a new project; left on, the app
  is only reachable by whoever owns the Vercel account, defeating the point of a public deploy.
- Every push to `master` auto-deploys (standard Vercel git integration) — this is what makes "add more games later"
  painless: push, and the frontend update ships itself.

## apps/api — Render

Deployed from `render.yaml` at the repo root via Render's **Blueprint** flow (Dashboard → New → Blueprint → this
repo). A few things that weren't obvious the first time through, kept here so they aren't rediscovered the hard way:

- **`preDeployCommand` is not available on Render's free plan.** The blueprint originally ran
  `prisma migrate deploy` as a preDeploy step (matching the sibling app's pattern); free-tier blueprint sync
  rejected it outright ("pre-deploy command is not supported for free tier services"). Fixed by folding the
  migration onto the end of `buildCommand` instead — still one-shot, still before the new release ever serves
  traffic, just not a distinct pipeline stage. Revisit if this ever moves to a paid plan.
- **Free plan allows only one active free Postgres instance per account.** An earlier ad-hoc database (created
  directly via the Render API before switching to the Blueprint flow) blocked the blueprint's own
  `fdg-postgres` from being created ("cannot have more than one active free tier database") until the orphan was
  deleted by hand in the dashboard.
- **`CORS_ORIGIN` has to match Vercel's *actual* assigned domain, not a guessed one.** The web service refuses to
  boot in production without an explicit origin (`apps/api/src/env.ts`), so this can't be silently skipped — but
  it's easy to set it to the wrong Vercel alias. Vercel commonly assigns a project a short bare `<name>.vercel.app`
  alias in addition to the longer `<name>-<account>.vercel.app` one; only the short one may end up being what the
  browser actually sends as `Origin`. Set both, comma-separated, as `CORS_ORIGIN` — check
  `apps/api/src/env.ts`'s CORS parsing for the exact allowed format. Get the real value from the deployed Vercel
  project's domain list, not from what you assume the project name will produce.
- **`DATABASE_URL` is wired via Render's native `fromDatabase` linking** (see `render.yaml`), so the connection
  string is never copied by hand and never has to pass through a chat, a script, or a `.env` file.
- **`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `ROOM_TOKEN_SECRET`** use Render's `generateValue: true` — a fresh
  random secret per var, generated by Render at blueprint-apply time. `apps/api/src/env.ts` refuses to boot in
  production without all three set to a real random value at least 32 characters long, and explicitly rejects
  every literal this repo has ever shipped as a dev placeholder (see `KNOWN_INSECURE_SECRETS`).
- **`FOOTBALL_DATA_PROVIDER=live`** — real ESPN + Wikidata data, not the offline fixture/replay provider. This is
  the actual point of a real deployment; see `packages/football-data/README.md` for what that wiring means.

### The 30-day free Postgres trap

**This applies to the database only, not the web service, not Vercel, not "the deployment" as a whole.** Render
deletes a **free-plan Postgres instance** 30 days after creation, with a 14-day grace period and no way back
(`render.yaml` has this as an inline comment next to the `databases:` block too, so it can't be missed on a future
read of that file). The `fdg-api` web service itself has no such expiry — free web services just sleep after 15
minutes idle and wake on the next request (`~30-60s` cold start), they don't get deleted.

**Created:** 2026-09-24. **Expires:** ~2026-10-24 (30-day mark), fully gone by ~2026-11-07 (after the grace period)
if not upgraded. Before then: either upgrade `fdg-postgres` to a paid plan in the Render dashboard (no code change
needed — the connection string stays wired the same way), or take a backup and accept the reset. Worth doing before
this holds anything a real user would mind losing (accounts, friendships, session history).

### Redeploying

Push to `master` — both `fdg-api` (via its GitHub trigger) and `football-drinking-game-web` (via Vercel's git
integration) redeploy automatically. No manual step for an ordinary code change. A change to `render.yaml` itself
needs a manual blueprint sync in the Render dashboard if auto-sync doesn't pick it up.

### Local reproduction of the production build

Before trusting a Render deploy, the exact `buildCommand` / `startCommand` pair in `render.yaml` can be run locally
from a clean tree — see the commit that introduced Postgres-everywhere for the verified transcript. In short:

```bash
rm -rf apps/*/dist packages/*/dist apps/*/tsconfig.tsbuildinfo packages/*/tsconfig.tsbuildinfo
npm install
npm exec --workspace=apps/api -- prisma generate
npx tsc -b tsconfig.build.json
npm exec --workspace=apps/api -- prisma migrate deploy   # needs DATABASE_URL pointed at a real (local or remote) Postgres
NODE_ENV=production PORT=4000 HOST=0.0.0.0 \
  JWT_ACCESS_SECRET=<32+ chars> JWT_REFRESH_SECRET=<32+ chars> ROOM_TOKEN_SECRET=<32+ chars> \
  CORS_ORIGIN=http://localhost:3000 FOOTBALL_DATA_PROVIDER=live \
  node apps/api/dist/index.js
curl localhost:4000/health   # expect {"ok":true}
```
